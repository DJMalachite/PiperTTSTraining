# The AMD BC-250

The BC-250 is a salvaged console APU — RDNA2, reporting as `gfx1013` ("Cyan
Skillfish") — sold cheaply as a compute board. It has no official ROCm support,
and getting compute working on it is genuinely hard.

**Read the summary before you plan around this board.** Almost everything here
comes from [akandr/bc250-rocm](https://github.com/akandr/bc250-rocm), which is
the most thorough public characterisation of the hardware. That work covers one
board, and its author notes reproducibility elsewhere is unknown — so this tool
**measures** rather than assumes. `./run doctor` runs a real autograd loop on
your board and tells you what actually happens.

## The summary

| | With a stock torch wheel | After `scripts/bc250/build.sh` |
| --- | --- | --- |
| Inference and matmul | Works, ~4.5 TFLOP/s at N=8192 with preallocated buffers | Same, faster with native rocBLAS |
| **Full training** | **Blocked** — see below | **Unproven. Measure it.** |
| Dataset preparation | Works (CPU, or GPU Whisper if compute is healthy) | Works |
| Export and synthesis | Works — inference is CPU-friendly anyway | Works |

The blocker for training with a stock wheel is specific, and it is not a
performance problem:

> the stock torch ROCm wheel ships **no gfx1013 elementwise kernels**, so
> autograd raises `invalid device function`

and separately:

> loops that **allocate and free GPU tensors every iteration** fault after 20 to
> 40 iterations

A training loop is precisely "autograd over elementwise ops, allocating every
iteration". Matmul with a preallocated output — `torch.mm(a, b, out=c)` — is what
works, and that is the shape of inference, not training.

Both have a cause you can address, which is what the rest of this document is
about. Neither has a published fix on this board, which is why nothing here
promises you a result.

## Why the kernels are missing, exactly

torch's GPU kernels are compiled **ahead of time, once per target** in
`torch.cuda.get_arch_list()`. Every published wheel lists the architectures AMD
supports; `gfx1013` is in none of them. So on this board:

- `torch.cuda.is_available()` returns `True` — the device enumerates fine;
- a matmul **succeeds** — GEMM comes from rocBLAS, a separate library loaded at
  runtime, not from torch's compiled kernels;
- `a + b` raises `invalid device function` — there is no compiled kernel for
  this architecture to launch.

That combination is why "the GPU works" and "training is blocked" are both true
at once, and why `./run doctor` asks the question directly:

```
[ok]   torch          torch 2.9.1 / ROCm 6.4 / AMD Custom GPU 0405 (gfx1013) / matmul OK
[warn] torch gfx kernels   this torch has no gfx1013 code (built for gfx900, gfx906, ..., gfx1201)
```

The only known way to change that answer is to compile torch for `gfx1013`,
which is what `scripts/bc250/build.sh` does.

## Building a torch that has the kernels

```bash
scripts/bc250/build.sh --list      # what is done and what is not
scripts/bc250/build.sh --dry-run   # every command, nothing executed
scripts/bc250/build.sh             # run the stages that are not done
```

Six stages. Each is idempotent and records its own completion, so an interrupted
run resumes rather than restarts. Stages 1–2 touch the host kernel and need a
reboot; 3–6 happen inside a Fedora container.

| Stage | Where | What | Acceptance |
| --- | --- | --- | --- |
| `detect` | host | Read-only. Board, kernel, module parameters, CU count, disk, tooling | Nothing unexpected |
| `kernel` | host, root | Patched amdgpu with all three fixes, then a reboot | Both module parameters readable, `active_cu_number 40` |
| `container` | host | Fedora 43 distrobox with ROCm and a toolchain | `rocminfo` reports `gfx1013` inside it |
| `rocblas` | box | Native gfx1013 rocBLAS | 56 gfx1013 Tensile libraries |
| `torch` | box | `PYTORCH_ROCM_ARCH=gfx1013`, hours | `get_arch_list()` contains `gfx1013` |
| `install` | box | Install the wheel, run the autograd probe | **The verdict** |

### Threads, and why memory decides

The torch build uses **every core by default**. The catch is that memory, not
cores, is what actually ends this build: torch's C++ link steps are the peak,
and the GPU has already taken half of the board's 16 GB, so 16 threads can mean
well under a gigabyte of headroom each. An OOM-killed link three hours in loses
the three hours.

The stage measures the budget, and when it does not match the job count it says
so and lets you decide rather than quietly picking for you. To keep all the
threads, give it somewhere to spill — swap is only touched at the peak:

```bash
sudo fallocate -l 16G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
```

Or build with fewer:

```bash
scripts/bc250/build.sh --stage torch --jobs 6
```

`--jobs` (or `BC250_MAX_JOBS`) overrides in either direction. The kernel stage
already uses every core; it is small enough that memory never becomes the
constraint.

### Stopping, resuming and resetting

A stage is marked done only once it exits cleanly, so **an interrupted build
does not need resetting — run it again.** It resumes at the stage that did not
finish, and the expensive stages resume rather than restart: the kernel tarball
is cached, and torch's build tree is incremental, so a `torch` stage killed at
hour three picks up near hour three.

`--reset` is for when a stage's own artefacts are the problem — a half-applied
patch, a wedged build tree — not for ordinary interruptions:

```bash
scripts/bc250/build.sh --reset torch     # one stage
scripts/bc250/build.sh --reset all       # everything
scripts/bc250/build.sh --reset torch --dry-run   # just show me
```

It lists exactly what it will delete and asks first. What it deliberately does
*not* touch:

- **the downloaded kernel tarball** — expensive to fetch, cheap to re-extract,
  so `--reset kernel` removes only the patched source tree;
- **the patched amdgpu module already installed on the host.** That is undone by
  restoring the `.bc250-backup-*` file stage 2 printed, not by deleting
  anything. Nothing here can put your display back; that backup can.

`--reset torch` deletes the built wheel, which is the one that costs hours. It
says so before asking.

**Is it going to work?** Unknown, and this document will not pretend otherwise.
What is known: the same approach works for `gfx1010`, which is the same ISA
family and equally unsupported
([Efenstor/PyTorch-ROCm-gfx1010](https://github.com/Efenstor/PyTorch-ROCm-gfx1010-Debian13)),
and the allocation-churn fault has a kernel-side fix in `bc250_flush_by_runlist`.
What is not known is whether anything else on this board fails once those two are
out of the way. Nobody has published a result either way. If you get one — in
either direction — it is worth reporting to the reference repo.

### Why a Fedora container

The reference work was done on Fedora 43 with ROCm 6.4, its rocBLAS build script
expects a system ROCm laid out the way Fedora lays it out, and Fedora packages
ROCm in its own repositories. On CachyOS those scripts become something you
adapt rather than run, and adapting them is the part most likely to go wrong.

Training runs inside the container too. A torch built from source links against
the container's `/usr` ROCm rather than bundling its own, so the wheel is only
meaningful where those libraries are — which also means there is nothing to
graft into the host and no ABI to match.

The cost is a second environment. `PIPERTRAINER_ENV=bc250` puts it in
`.venv-bc250` and `.state-bc250`, beside whatever the host has.

### Working in the container day to day

**Everything that touches the GPU runs inside the box.** That is `setup`,
`train`, `resume`, `preview`, `export`, `monitor` and `doctor`:

```bash
distrobox enter bc250
cd ~/PiperTTSTraining
./run doctor
./run train
```

No `PIPERTRAINER_ENV=` prefix: stage 3 writes it into the container's
`/etc/profile.d/` and `/etc/bashrc`, so every shell in there already is the
bc250 environment. Confirm with `echo $PIPERTRAINER_ENV` — if it is empty,
prefix your commands and say so, because something did not take.

The container shares `$HOME`, so it is the same clone, the same `data/`, the
same `runs/` and the same profiles on both sides. Only the installed
environment differs. `$HOME` being shared is also exactly why `./run` must not
guess: on the host the same command has to keep finding `.venv`.

| Command | Where | Why |
| --- | --- | --- |
| `setup` | box | Stage 6 already ran it. Only repeat it to change something. |
| `doctor`, `train`, `resume`, `preview`, `monitor` | box | Needs the gfx1013 torch |
| `export` | box or host | ONNX export runs on CPU either way |
| `dataset` | either | Needs ffmpeg. That is optional in the box, so if it was not installed, build datasets on the host |
| `smoke` | box | CPU-only, but it proves *this* install works end to end |

`./run monitor` serves TensorBoard on port 6006. distrobox shares the host's
network namespace, so `http://localhost:6006` in a host browser just works.

You do not need a host install at all. If you want one anyway — for CPU
training or dataset work while the GPU is busy — run a plain `./run setup` on
the host with no `PIPERTRAINER_ENV` set, and the two live side by side.

### What is different on CachyOS

Every published BC-250 script targets Fedora. Three things differ on Arch, and
each of them costs you a display if got wrong — `scripts/bc250/build.sh` handles
all three, but know them before you run it:

- **Modules are compressed with zstd, not xz.** The widely repeated
  `xz --check=crc32` advice is Fedora-specific (the xz default of crc64 loads
  via `modprobe` but fails the in-kernel decompressor). Here the module is
  `amdgpu.ko.zst`; the script matches whatever is already installed rather than
  guessing, and backs the original up first. **Keep that backup** — restoring it
  is how you get your display back.
- **The toolchain has to match.** CachyOS frequently ships clang/LTO kernels, so
  the module build passes `LLVM=1` when `/proc/version` says clang.
- **The initramfs generator is mkinitcpio, not dracut.**

Kernel source is fetched from kernel.org — only the AMD subtree — because no
distribution's `-headers` package contains the driver source you need to rebuild
it.

### The three kernel fixes

They come from two different projects, and all three go on one tree:

| Fix | Source |
| --- | --- |
| `bc250_cc_write_mode`, 40-CU unlock | [duggasco/bc250-40cu-unlock](https://github.com/duggasco/bc250-40cu-unlock) — a separate project |
| `bc250_flush_by_runlist` | [the reference repo](https://github.com/akandr/bc250-rocm), `scripts/apply_runlist_flush.py` |
| PASID flush via MMIO | the reference repo, `patches/amdgpu-flush-pasid-mmio.patch` |

`bc250_cc_write_mode=3` writes the CC and SPI shader-array configuration
registers during `gfx_v10_0_get_cu_info()`, guarded to PCI device `0x13FE`; both
register writes are needed, neither alone produces the compute scaling.
`bc250_flush_by_runlist=1` rebuilds the runlist on unmap — **this is the fix for
the allocation-churn fault**, which is to say the second of the two things that
block training. The third has no module parameter: `flush_pasid_uses_kiq = false`
in `gmc_v10_0.c` routes the PASID TLB flush via MMIO instead of KIQ, fixing
silently dropped stores (that is: *wrong results*, not crashes).

Both parameters belong on the kernel command line as well as in
`/etc/modprobe.d/`, because amdgpu loads from the initramfs:

```
amdgpu.bc250_cc_write_mode=3 amdgpu.bc250_flush_by_runlist=1
```

The pinned commits for both projects are in `pins.toml` under `[bc250]`; the
scripts read them from there, so the code and the documentation cannot disagree
about which revision is being applied.

**Kernel 7.1.5 or newer.** On older kernels the correctness fix forces the board
to 24 CU, where compute wedges. On 7.1.5 the 40-CU unlock and the corrected
flush can coexist.

**Do not set `amdgpu.sched_policy=2`.** Hardware scheduling must stay at the
default. This was the workaround on older kernels; with the patched module on
7.1.5 it is the difference between a wedge and a clean run.

**Power-cycle, do not soft-reboot,** after a compute wedge.

### rocBLAS: optional, and it does not finish unaided

**Stage 4 is optional and it is expected to stop short.** Run it if you want,
but do not let it block you:

```bash
scripts/bc250/build.sh --skip rocblas
```

`scripts/build_rocblas_gfx1013.sh` in the reference repo gets as far as
generating gfx1013 Tensile code objects — about 55 of them — and then fails the
manifest verify without linking `librocblas.so`. That is not a mistake on your
part and re-running does not fix it. rocBLAS re-fetches its own copy of Tensile
into `build/release/virtualenv` during configure, and that copy has no gfx1013
in `SupportedISA`, so the assembly kernels the manifest expects never appear.

The script's step 4 says to add them by hand — `SupportedISA` and `AsmCaps` in
the fetched Tensile, the `Processor` and `LazyLoadingInit` enums, and the
`deviceString` branches in rocBLAS — but **step 4 is only an `echo`**. It
patches nothing, and the reference repo does not write the edits down anywhere
either. Its own note concedes the point.

So this stage is a genuine dead end unless you want to derive those edits
yourself. Skipping it costs matmul throughput and nothing else: rocBLAS is the
**GEMM** library, and the kernels that block training are torch's own
elementwise and convolution kernels, which come from stage 5. `./run doctor`
reports missing gfx1013 rocBLAS as a warning for exactly that reason, and a
skipped stage 4 is recorded as `skipped` rather than `done`.

If it does link, stage 4 installs to `/opt/bc250/rocm`, reachable through
`ROCBLAS_TENSILE_LIBPATH` and `LD_LIBRARY_PATH` rather than overwriting the
system copy. It refuses to install anything if no library was produced — an
earlier version installed the Tensile objects alone and reported success, which
left `LD_LIBRARY_PATH` pointing at a directory with no library in it.

## What this tool does about the board

Set `runtime.hardware: bc250` in your profile, or leave it at `auto` and let it
be detected from the reported gfx target. That activates a hardware profile which:

- sets **`HSA_ENABLE_SDMA=0`** for every training and inference subprocess — the
  SDMA host-to-device path is broken for bulk transfers on this board;
- sets **`TORCH_BLAS_PREFER_HIPBLASLT=0`** — hipBLASLt has no gfx1013 support at
  all and torch reaches for it first, so without this the rocBLAS you built never
  gets used;
- sets **`MIOPEN_FIND_MODE=FAST`** — MIOpen has no tuning entries for an
  architecture nobody supports, and its default search compiles and benchmarks
  every solver at runtime on first use;
- **refuses to set `HSA_OVERRIDE_GFX_VERSION`** (see below);
- forces conservative settings: `trainer.precision: 32-true` (fp16 batch-GEMM
  crashes in the rocBLAS layer), `data.batch_size: 4`, `data.num_workers: 1`,
  `dataset.max_seconds: 10.0`;
- adds the system checks below to `./run doctor`;
- runs a real autograd probe before you commit to a run, and offers to switch to
  CPU if it fails.

## `HSA_OVERRIDE_GFX_VERSION` is a dead end here

This is the most common piece of BC-250 advice on the internet, and it is wrong
for real workloads. gfx1010 and gfx1013 share an ISA, which makes
`HSA_OVERRIDE_GFX_VERSION=10.1.0` look like a free fix — but:

> the memory-aperture layout differs, so anything using scratch or private
> addressing hits `HSA_STATUS_ERROR_MEMORY_APERTURE_VIOLATION`

An earlier version of this tool applied `10.3.0` automatically for gfx1013,
which is further off still (that is gfx1030, a different RDNA2 part). It no
longer does: `hardware.BC250.banned_env` records the variable as banned with the
reason, `env.needs_gfx_override` never suggests it, and there is a regression
test. The override table still applies to the targets it genuinely rescues —
gfx1011/1012 to 10.1.0, gfx1031–1036 to 10.3.0.

Note that compiling torch for `gfx1013` is the *opposite* of overriding: it
produces real kernels for the real architecture rather than lying to the runtime
about which architecture this is.

If you set the override yourself in `runtime.env`, the tool respects you and
`./run doctor` notes it.

## What `./run doctor` reports

With the `bc250` profile active you get a `Hardware profile: bc250` section
checking: kernel version, both module parameters, that `sched_policy` is
unset, `active_cu_number`, `HSA_ENABLE_SDMA`, and whether a rocBLAS with gfx1013
kernels is reachable. The GPU section separately reports whether the installed
torch carries gfx1013 code at all. Then it runs the autograd probe.

The probe is the important one. It builds a small model using the layer types a
VITS vocoder actually uses — `Conv1d`, `ConvTranspose1d`, LeakyReLU, elementwise
arithmetic — and runs 60 optimizer steps, allocating fresh tensors each
iteration. That reaches both documented failure modes; a matmul reaches neither.

How a probe failure is reported depends on what torch turned out to be:

- **torch has no gfx1013 kernels** — a **warning**. It confirms the
  documentation rather than indicating something is broken.
- **torch does have gfx1013 kernels** — a **failure**. The documented cause has
  been removed, so the failure is new information. Capture it and report it.

## So how do I train a voice?

Everything except GPU training works on this machine regardless. In order of
least effort:

**1. Prepare the dataset here, train elsewhere.** Dataset preparation is the part
that benefits from being on the machine with the recording, and it works. Then:

```bash
rsync -av data/myvoice/ othermachine:~/PiperTTSTraining/data/myvoice/
rsync -av profiles/myvoice.yaml othermachine:~/PiperTTSTraining/profiles/
```

Run `./run setup` and `./run train` on the other machine. Delete
`runtime.hardware` and `runtime.env` from the copied profile — those describe
this box, not that one. Everything else is portable.

**2. Train on CPU here.** Slow, but correct, and the wizard offers to switch for
you. Fine-tuning from a pretrained checkpoint helps enormously. Use
`voice.quality: low` (16 kHz) to cut the work substantially.

**3. Build torch for gfx1013** — `scripts/bc250/build.sh`, described above. The
torch build alone is hours on this board. It is also portable: the container is
the build environment, so the same Fedora 43 image on a faster machine produces
a wheel that works here. Drop it in `.state/bc250/wheels/` and run the `install`
stage.

## If your board disagrees

Entirely possible — this is one board's characterisation. If the autograd probe
passes on yours, the wizard says so and proceeds on GPU. That is the whole point
of measuring: the tool defers to your hardware over the documentation.
